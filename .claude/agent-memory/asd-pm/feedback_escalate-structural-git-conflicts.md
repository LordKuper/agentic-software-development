When a phase workflow's literal git instruction is unexecutable or collides with a `git-strategy.md` "Forbidden" rule, HALT and present options rather than choosing. Do not treat "the workflow says X" as settling it when X is impossible.

**Why:** In the sprint 001 `pr` merge phase the workflow said to push the archive commit "to sprint branch", but this repo squash-merges with auto-delete-branch, so the remote sprint branch was already gone and the local one held obsolete pre-squash history. The only other obvious route — committing to `main` — is forbidden outright by `git-strategy.md` and blocked by branch protection. The user explicitly asked to be consulted "on something this structural" and then chose a third option (a follow-up `chore/archive-sprint-NNN` PR off `main`) that neither document named. Guessing would have produced either a resurrected dead branch or a rule violation.

**How to apply:** Escalation is the right call whenever the choice changes where commits permanently live, not merely how they are worded. The validated resolution pattern for post-merge archival: branch off `main`, `git mv` + `state.json` update + decisions-log append, one commit, open a PR, let the user merge — never merge it yourself.

**Fixed at the root, 2026-09-03 (outside any sprint, direct maintenance patch per user request).** The user wanted this manual follow-up to stop recurring, but explicitly rejected framing it as an exception to "never push directly to `git.base_branch`" — that rule stays absolute, no exceptions, every base-branch change goes through a PR, full stop. The actual fix is narrower: `git-strategy.md`'s new "Finalize PR (autonomous)" section says PM opens **and merges (squash) itself** the one `chore/finalize-sprint-NNN` PR for this terminal-state write — still 100% PR-mediated, just no user confirmation gate for this specific, mechanical, three-field, no-code PR, run only after the sprint's own PR is already confirmed merged. `asd-phase-pr.md` step 2 and `sprint-lifecycle.md` "PR phase" match. **Do not revert to "never merge it yourself" for this one PR class** — superseded. Still escalate on any OTHER git conflict this note's opening paragraph describes, and never treat this as license to merge the sprint's OWN PR without asking — that confirmation gate (`checkpoints.md` "confirms PR opening") is untouched. Tag push and `gh release create` remain unaffected — no protected branch involved. See [[design-vs-docs-disambiguation]] for the related habit of resolving ambiguity per-site rather than by blanket rule.
