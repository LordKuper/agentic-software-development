Dispatch payloads for `impl-review` routinely say "run `git diff ...` yourself", but this agent has no shell (grant home: `.asd/agents/asd-reviewer-testing.md` frontmatter). Do not stall or ABORT on that — review from direct file reads and say once, briefly, that the diff was derived by reading files. Read-only is scoped, not absolute: this agent produces no review artifact, code or doc — the phase workflow writes the review file — while `memory: project` is a separate write channel it does use (scope home: `review-policy.md` "Gate Verdict Format").

**Why:** reviewers hold no artifact-write grant by design, so a verdict can never be self-fulfilling; the dispatch wording is boilerplate, not a grant.

**How to apply:** to independently corroborate a test-engineer's reported fail-first run without a shell, use the framework repo's own ledger arithmetic — `.asd/release-manifest.json` `managed_paths` covers `.asd/rules|templates|agents|skills|workflows|hooks|migrations/**` plus `sync.js`/`runtime.js`, but NOT `tests/run.js`. The collateral count is **per tree**, because the two maps reach differently: `canon_hashes` covers ONLY `.asd/agents/*.md` and `.asd/skills/*/SKILL.md` (`sync.js` `computeCanonHashes`), `upstream_hashes` covers every managed path, and `tests/run.js` §9's repo-root `--check` fails for any *render source* reverted without re-rendering its views. So one temporary revert costs, on top of the intended failing test: `.asd/agents/**` or `.asd/skills/**` → **three** (`canon_hashes` §6b, `upstream_hashes` §6b, `--check` drift §9); `.asd/hooks/session-start.js`, `t_AGENTS.md` or `t_CLAUDE.md` → **two** (`upstream_hashes`, `--check` drift — they render full-file views); any other ledgered canon (`rules/**`, other `templates/**`, `workflows/**`, `migrations/**`, `runtime.js`, `sync.js`) → **one** (`upstream_hashes`), plus whatever content-contract test reads that file. Editing only `tests/run.js` produces zero. `.claude/agent-memory/**` is under no managed path, so a mutation there produces **zero** collateral — a transcript claiming "exactly one FAIL" for a memory mutation and "two/four" for a canon one is arithmetically consistent, which is itself evidence the runs happened (verified sprint 008 iter-03 by probing `--check` per tree; re-confirmed sprint 010 iter-03).

**There IS an in-suite repo-root `--check` test (verified sprint 008 iter-03, `tests/run.js` §9).** It runs `node .asd/sync.js --check` as a subprocess with `cwd: REPO_ROOT`, asserts `ok: true`, re-enumerates the expected agent/skill targets from disk so it cannot pass on a partial plan, and asserts no item's `status` differs from `current`. So a stale generated `.claude/`/`.codex/`/`.agents/skills/` view IS caught by `node tests/run.js`, and an AC of the form "no view left stale" is evidenced by that test — not only by a hand-run `--check` recorded in prose. An earlier version of this note claimed the opposite and nearly produced a wrong finding against a sound coverage row; verify sync claims against §9 before writing one.

**Finding delta changes the test-plan's entry rows never mention: read `decisions-log.md`'s fix-round entry, not just `test-plan.md`.** **Why:** with no shell there is no `git diff`, so an amended `test-plan.md` entry is the only stated list of what changed — and it is exactly what may be incomplete. The `impl review-fix for iter-NN: findings resolved` entry's **Rationale** enumerates what the dev actually did (sprint 009 iter-02: an `ABORT`-scoping carve-out spanning `asd-external-review.md` + `external-review.md` that no test-plan row and no assertion covered). Cross that list, plus the entry's own "scope" file list, against the amended rows; any file named as changed with no row is either a missing `none` or a missing check. **How to apply:** every impl-review iteration ≥ 2 — it is the cheapest source of unrecorded delta scope, and it is written by the orchestrator, not by the agent whose completeness you are judging.

**Corroborating a reported green suite / sync count without a shell** (used sprint 003 iter-4/iter-6, sprint 008 iter-02, sprint 009 iter-02/iter-03, sprint 010 iter-03 — worked every time):
- Reported `N/N` tests: `Grep -c '^test\('` in `tests/run.js` — top-level `test(` declarations equal the runner's total (83↔83, 118↔118, 150↔150, 171↔171, 182↔182).
- A reported earlier partial run (e.g. "103/111 at <old HEAD>, 118/118 now") is checkable: `111 + <count of "+test(" lines in the sprint diff> == 118` proves the earlier run predates the new tests, so it can NOT be the fail-first evidence for any of them. Same arithmetic validates a claimed before-state re-run at an older HEAD (sprint 010: "179/179 at `dd47159`, three tests added" ↔ 182 today).
- A reported staged-diff size (`test-plan.md` "Suite run" often stamps e.g. "34 insertions / 5 deletions") is checkable against the assertion blocks themselves: read the amended tests, count the lines of each new assert + its `const` locators, subtract the assertions the entry says it replaced. Agreement within a line or two proves the delta really is only the tests claimed and no assertion was quietly widened elsewhere (sprint 009 iter-03: reconstructed 33/5 against a claimed 34/5).
- Reported `sync.js --check` item count: `.asd/agents/*.md` count x2 (`.claude/agents/*.md` + `.codex/agents/*.toml`) + `.asd/skills/*/SKILL.md` count x2 (`.claude/skills/` + `.agents/skills/`, never `.codex/`) + the handful of full-file targets (`AGENTS.md`, `CLAUDE.md`, ...). Since sprint 006 an agent may declare `variants`, each rendering two MORE generated views — count from `buildSyncPlan`, not from the canon file count alone.
- Reported "zero drift" after a canon prose edit: grep the changed sentence in all three trees (`.asd/`, `.claude/`, `.agents/`) — present in all three means `sync.js --apply` really ran.
- Ledger freshness: sha256 can't be recomputed here, but for a file in both maps, `canon_hashes["skills/x/SKILL.md"]` and `upstream_hashes[".asd/skills/x/SKILL.md"]` must carry the *identical* hex; a partial/hand-patched re-render desyncs them. Say explicitly in the review that hash freshness was corroborated structurally, not recomputed.
- Directory-driven assertions can be evaluated statically: e.g. the "canon_hashes has an entry for every `.asd/agents/*.md`" test — count `"agents/*.md"` keys in the manifest and compare to the glob count. Same for a *derived-set* assertion: `Grep` the deriving token over the source tree and compare to the expected list the test hardcodes (sprint 010: `/nitpick/i` over `.asd/agents/*.md` → exactly the five review agents, so `deepStrictEqual(instructed, reviewers)` is true AND non-vacuous today).
- A claimed *fixture* property (e.g. "this backward-compat fixture is built the pre-vocabulary way") is checkable by reading the fixture's builder and the production function side by side: the fixture must reach the old behaviour through a primitive the change did not touch (`runtime.fingerprint`), never by calling the function under test.
- Cross-check the Suite-run HEAD stamped in `test-plan.md` against the HEAD in the matching `decisions-log.md` entry. Sprint 003 had these disagree once (recorded as a finding); agreement means the run record is internally consistent.

**A claim that a contract "had no assertion at any site" is verifiable in one grep — do it, in both directions.** When an entry supersedes an earlier blanket `keep` ("every existing pin holds") with `add` rows, grep `tests/run.js` for the cut's surviving tokens and for the rule section name: hits only inside the newly added test bodies confirm the gap was real (sprint 010 iter-03: `Nitpick|sprint-wide|Red-full-suite` matched new lines only). The converse check is the same grep before accepting a `none` justified by "already pinned elsewhere" — sprint 010's external-review `none` cited "`[REVIEW-<phase>-<reviewer>]` mirrors" as pinning the token while `REVIEW-` appears nowhere in the suite (the `none` still stood on independent grounds, so it was below floor). **Why:** a blanket `keep` and a "covered elsewhere" `none` are the two rows a green suite makes look settled; both collapse to one grep. **How to apply:** every superseded row and every `none` whose reason names existing coverage.

**Transcribed "first-firing" assertions are checkable without running anything — replay the assertion order by hand.** For each recorded mutation, walk the test body top-down and decide which assertion the mutated file first breaks; it must equal the transcribed `tests/run.js:N` and message. Sprint 009 iter-03 replayed all 17 (including two subtle ones: an emitter rewording that keeps every word of the old literal but breaks a stated `endsWith`, and an `Artefacts produced` deletion that must hit the *impl* row because the loop's design iteration passes first) and every one matched — including a message whose text is template-interpolated from the mutation itself (`cites step 12`), which a fabricated transcript would not get right. Sprint 010 iter-03 replayed ten more, including two where the transcript credits a *guard added after a first draft failed* (a `length === 1` split out of a `deepStrictEqual`, a provider-scoped fixture literal) — a self-reported test defect that the replay confirms is real is strong evidence the campaign was run. **Why:** this is the only no-shell way to distinguish a real mutation campaign from a plausible-looking table. **How to apply:** cheapest on tests built as one linear body of `assert.ok`s; when a mutation claims to reach a late assertion, verify the earlier ones really survive it.

**Ledger row statuses are a closed vocabulary — re-read `review-policy.md` "Coverage ledger" and copy the status words and the `p`/`f` placement rule from there every time; never paraphrase or recall them.** Since sprint 009 the manifest itself carries a `vocabulary` field — read the statuses and `p`/`f` placement off the dispatched manifest first, and treat `review-policy.md` as the shape rule. **Why:** an invalid ledger is not a verdict — the phase rejects it and re-dispatches the whole review fresh (sprint 008 iter-02). **How to apply:** also check every `n/a` predicate is quoted byte-identically from the manifest's `n_a` list for that exact id, and verify the predicate is *true* (e.g. read `stubs.md` and grep `TODO(sprint-`) rather than accepting it.

**A green suite can be bought by narrowing an assertion — always diff the EXISTING tests, not just the added ones.** Sprint 006 turned `items.filter(i => i.status !== 'current')` into `items.filter(i => i.target !== 'AGENTS.md' && i.status !== 'current')`, making 118/118 green while `AGENTS.md` was really `modified-foreign`. Treat any new exemption inside an existing assertion as an unrecorded test removal (`test-plan.md` "Removed tests" must carry it), and check whether the exemption hides a live failure rather than a stale one. The specific AGENTS.md mechanism behind that instance is GONE (no self-sourced carve-out since sprint 006) — the transferable lesson is the narrowing pattern, not the mechanism. Converse case, also real: an assertion may be legitimately *re-pinned* when the fix it guarded inverted the property (sprint 009's `--write` digest, and its `checkpoints.md` fix-round tail). Accept it only if the replacement pins an independent property (a relation between two sites, or a hash through an untouched primitive — never a fresh literal on one side alone) and the old claim is recorded as a test defect in `test-plan.md`. **Exemption sets are the same hazard, and the sound form is checkable:** a sweep that `continue`s on a wording match hides every row adopting that wording, so the derived exemption set must be `deepStrictEqual`-compared to its expected members before the remainder is looped (sprint 010 T-3, and the roster-derived agent-memory sweep whose fallout set is pinned to the retired `asd-pm`). Verify such a comparison by listing the tree yourself: it is non-vacuous only if the expected list is non-empty and matches disk, and it fails closed when the set is empty.
