Dispatch payloads for `impl-review` routinely say "run `git diff ...` yourself", but this agent has no shell (grant home: `.asd/agents/asd-reviewer-testing.md` frontmatter). Do not stall or ABORT on that — review from direct file reads and say once, briefly, that the diff was derived by reading files. Read-only is scoped, not absolute: this agent produces no review artifact, code or doc — the phase workflow writes the review file — while `memory: project` is a separate write channel it does use (scope home: `review-policy.md` "Gate Verdict Format").

**Why:** reviewers hold no artifact-write grant by design, so a verdict can never be self-fulfilling; the dispatch wording is boilerplate, not a grant.

**How to apply:** to independently corroborate a test-engineer's reported fail-first run without a shell, use the framework repo's own ledger arithmetic — `.asd/release-manifest.json` `managed_paths` covers `.asd/rules|templates|agents|skills|workflows|hooks|migrations/**` plus `sync.js`/`runtime.js`, but NOT `tests/run.js`. The collateral count is **per tree**, because the two maps reach differently: `canon_hashes` covers ONLY `.asd/agents/*.md` and `.asd/skills/*/SKILL.md` (`sync.js` `computeCanonHashes`), `upstream_hashes` covers every managed path, and `tests/run.js` §9's repo-root `--check` fails for any *render source* reverted without re-rendering its views. So one temporary revert costs, on top of the intended failing test: `.asd/agents/**` or `.asd/skills/**` → **three** (`canon_hashes` §6b, `upstream_hashes` §6b, `--check` drift §9); `.asd/hooks/session-start.js`, `t_AGENTS.md` or `t_CLAUDE.md` → **two** (`upstream_hashes`, `--check` drift — they render full-file views); any other ledgered canon (`rules/**`, other `templates/**`, `workflows/**`, `migrations/**`, `runtime.js`, `sync.js`) → **one** (`upstream_hashes`), plus whatever content-contract test reads that file. Editing only `tests/run.js` produces zero. Verified sprint 008 iter-03 by probing `--check` per tree. If a reported fail-first count matches, the run was almost certainly real; if not, probe harder.

**There IS an in-suite repo-root `--check` test (verified sprint 008 iter-03, `tests/run.js` §9).** It runs `node .asd/sync.js --check` as a subprocess with `cwd: REPO_ROOT`, asserts `ok: true`, re-enumerates the expected agent/skill targets from disk so it cannot pass on a partial plan, and asserts no item's `status` differs from `current`. So a stale generated `.claude/`/`.codex/`/`.agents/skills/` view IS caught by `node tests/run.js`, and an AC of the form "no view left stale" is evidenced by that test — not only by a hand-run `--check` recorded in prose. An earlier version of this note claimed the opposite and nearly produced a wrong finding against a sound coverage row; verify sync claims against §9 before writing one.

**Corroborating a reported green suite / sync count without a shell** (used sprint 003 iter-4/iter-6, sprint 008 iter-02 — worked every time):
- Reported `N/N` tests: `Grep -c '^test\('` in `tests/run.js` — top-level `test(` declarations equal the runner's total (83↔83, 118↔118, 150↔150).
- A reported earlier partial run (e.g. "103/111 at <old HEAD>, 118/118 now") is checkable: `111 + <count of "+test(" lines in the sprint diff> == 118` proves the earlier run predates the new tests, so it can NOT be the fail-first evidence for any of them.
- Reported `sync.js --check` item count: `.asd/agents/*.md` count x2 (`.claude/agents/*.md` + `.codex/agents/*.toml`) + `.asd/skills/*/SKILL.md` count x2 (`.claude/skills/` + `.agents/skills/`, never `.codex/`) + the handful of full-file targets (`AGENTS.md`, `CLAUDE.md`, ...). Since sprint 006 an agent may declare `variants`, each rendering two MORE generated views — count from `buildSyncPlan`, not from the canon file count alone.
- Reported "zero drift" after a canon prose edit: grep the changed sentence in all three trees (`.asd/`, `.claude/`, `.agents/`) — present in all three means `sync.js --apply` really ran.
- Ledger freshness: sha256 can't be recomputed here, but for a file in both maps, `canon_hashes["skills/x/SKILL.md"]` and `upstream_hashes[".asd/skills/x/SKILL.md"]` must carry the *identical* hex; a partial/hand-patched re-render desyncs them. Say explicitly in the review that hash freshness was corroborated structurally, not recomputed.
- Directory-driven assertions can be evaluated statically: e.g. the "canon_hashes has an entry for every `.asd/agents/*.md`" test — count `"agents/*.md"` keys in the manifest and compare to the glob count.
- Cross-check the Suite-run HEAD stamped in `test-plan.md` against the HEAD in the matching `decisions-log.md` entry. Sprint 003 had these disagree once (recorded as a finding); agreement means the run record is internally consistent.

**Ledger row statuses are a closed vocabulary — re-read `review-policy.md` "Coverage ledger" and copy the status words and the `p`/`f` placement rule from there every time; never paraphrase or recall them.** **Why:** an invalid ledger is not a verdict — the phase rejects it and re-dispatches the whole review fresh (sprint 008 iter-02). **How to apply:** also check every `n/a` predicate is quoted byte-identically from the manifest's `n_a` list for that exact id.

**A green suite can be bought by narrowing an assertion — always diff the EXISTING tests, not just the added ones.** Sprint 006 turned `items.filter(i => i.status !== 'current')` into `items.filter(i => i.target !== 'AGENTS.md' && i.status !== 'current')`, making 118/118 green while `AGENTS.md` was really `modified-foreign`. Treat any new exemption inside an existing assertion as an unrecorded test removal (`test-plan.md` "Removed tests" must carry it), and check whether the exemption hides a live failure rather than a stale one. The specific AGENTS.md mechanism behind that instance is GONE (no self-sourced carve-out since sprint 006) — the transferable lesson is the narrowing pattern, not the mechanism.
