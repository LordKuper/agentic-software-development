This repo (`D:\Projects\agentic-software-development`) IS the ASD framework's source, not a consumer project. `tests/run.js` (zero-dependency runner, no package.json/build) only covers `.asd/sync.js` and `.asd/skills/asd-update/update.js` engine behaviour — it has no fixture class for rules/templates/agents/skills *content* (e.g. no "no bare `design/`" grep-guard test). Prose/path rename sprints are verified by repo-wide `git grep` sweeps run directly in impl and re-verified independently in impl-test, not by new `tests/run.js` fixtures — adding a content-grep unit test for a one-time rename was explicitly rejected as disproportionate new-infrastructure cost.

Suite gate here = three commands: `node tests/run.js` (test), `git diff --check` (lint), `node .asd/sync.js --check` (build). `sync.js --check` always exits 0 with `ok:true` for non-orphan drift (stale/missing/modified-foreign) — only a marked orphan flips `ok:false`/exit 1. Any assertion trusting bare `ok`/`items` shape alone is a vacuous-pass risk for everything except orphans. This pattern recurred: one fix added a `status === 'current'` per-item assertion; a later review found *that* still passed vacuously if the plan-builder silently dropped a whole canon directory from enumeration (shrinking the item list rather than marking anything stale) — fixed by independently enumerating canon sources from disk and asserting each expected target string appears in the plan before filtering for drift.

`.asd/release-manifest.json`'s `upstream_hashes` ledger is a separate, easy-to-miss drift source: it is NOT recomputed by editing canon alone, only by running `node .asd/sync.js --apply <file...>` afterward (the mechanical hash-ledger recompute step). A canon edit landed without that follow-up reads green on `sync.js --check` (exit 0, `ok:true`) yet fails the dedicated `tests/run.js` integrity assertion — recurred at least twice in one sprint (once for a managed-block target, once for four rule/template/workflow files after an unrelated fix cycle). Always a test/repo-state defect for a dev to fix via `sync-apply`, never something this agent's write scope covers (`.asd/release-manifest.json` is outside the tester's write scope).

**How to apply**: when reviewing/extending drift-detection or "everything green" style assertions in this codebase, always ask "can this pass if the checked collection is empty or a subset?" — that's the exact defect class recurring in this repo's own test suite. When asked to verify such an assertion's own logic (not just its pass/fail), independently confirm the field names/string construction it relies on rather than trusting a green run alone. When the full suite goes red on a canon-hash-ledger assertion right after unrelated production fixes landed, check first whether `sync.js --apply` on the touched canon files was simply never re-run — file it as a defect, don't hand-fix the ledger.
