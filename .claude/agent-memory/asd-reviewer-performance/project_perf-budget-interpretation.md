In this repo (the ASD framework, `self_hosting: enabled`), `.asd/project/custom-coding-rules.md` has **no perf budgets section** — its three rules are zero-dependency/sync-discipline constraints, not latency/memory/throughput budgets. `custom-common-rules.md` has none either. (Re-verified 2026-09-01, sprint 002 iter 5.) The formal stop condition ("no budgets → APPROVE with note") therefore fires on almost every sprint here.

The only executable surfaces that can carry real perf risk are six files: `.asd/sync.js`, `.asd/skills/asd-update/update.js`, `tests/run.js`, and the three `session-start.js` hooks (two of which are generated).

**Why:** the "product" is agent-runtime instructions, so the closest thing to a perf budget is `AGENTS.md`'s hard rule "Every change must minimize runtime tokens". Treating that as the surrogate budget makes the review substantive instead of a rubber stamp on prose-only sprints.

**How to apply:** when a diff touches none of the six executable files, mark the classic rubric (`anti-patterns`, `algorithmic complexity`, `hot path`) `n/a` with that evidence, but still actively check (a) net prose/token delta against the AGENTS.md rule, and (b) any string that is *executable data* rather than prose — the `':(exclude)…'` git pathspecs in `external-review.md` / `asd-external-review.md` / `t_prompt-external-impl.md` (they size the external-review diff payload; self-hosting row = 5 excludes, `.asd/project`/`.asd/sprints`/`.claude`/`.codex`/`.agents/skills`) and `.asd/release-manifest.json` `managed_paths` cardinality (it sizes what `update.js` parses; `canon_hashes`/`upstream_hashes` churn is value-only and free). Escalate to a real finding only if one of those grows. `managed_paths` is directory-level (7 entries), so file renames *inside* a tracked tree never grow it. Also cheap and high-value: grep `"model"`/`"effort"` across `.asd/agents/*.md` — a family/effort tier bump is a direct dispatch-cost regression that no other reviewer owns. (Roster re-verified sprint 002 iter 5: 7 internal reviewers + BA/architect/UX = opus/high, external = fable/high, PM = opus/medium, both devs + test-engineer = sonnet/medium. Any deviation is the finding.)

**Cost model for the two hot-path executables** (established sprint 002 iter 4, the first dispatch here with a real `.js` file in scope):
- `session-start.js` runs once per session and is dominated by Node process startup (~30–50 ms) plus one `readdirSync` of `.asd/sprints/` and one `readFileSync`+`JSON.parse` per sprint dir. Everything downstream of that — `PHASE_CHAIN.indexOf`, `Object.keys(verdicts).sort()`, the verdict scans in `lastReviewVerdict` — operates on collections bounded by *framework structure*, not user input: 11 phases, ≤15 iteration keys (`review-policy.md` cap), and ≤8 verdict entries (7 internal reviewers + external). Three or four sequential short-circuiting `some`/`every` passes over ≤8 strings (iter 5 added a `some(approved)` guard so an all-`skipped:` map reads `mixed`, not `green`), or a regex literal like `/^skipped:/` applied ≤8 times, is unmeasurable against process startup. **Micro-scrutiny of this function is always a non-finding — confirm in one line and move on.** Only a change that adds *filesystem* work per sprint dir, or unbounds one of those collections, is worth a finding.
- `tests/run.js` is ~77+ in-process tests plus a small fixed set of **subprocess spawns** — as of sprint 002 iter 5 there are five: `node .asd/sync.js --check` (section 9), `runHook('claude')`, `runHook('codex')`, and two temp-root `session-start.js` runs (the satisfied-`skipped:` test and the all-`skipped:`→`mixed` test). Each spawn costs ~50–150 ms on win32; in-process guards (e.g. the `.asd/templates/*.json` parse guard) are sub-millisecond. **Do not accept "this new test is sub-ms, like the JSON-parse guard" at face value when the test calls `execFileSync`** — it is 2–3 orders of magnitude more, and a dispatcher briefing may assert the wrong premise. It is still not a finding while spawn count grows by a bounded constant, since process-level output (the hook's stdout JSON) genuinely cannot be asserted in-process. Escalate only if spawns become *per-fixture* (a loop over files each spawning node) — that turns a constant into O(n) on a suite with no parallelism.

**Claimed-vs-delivered lens (dispatch-cost sprints).** When a sprint's `audit.md` carries a dispatch inventory with per-verdict savings (e.g. sprint 002's `P-N` rows: "−6 opus/high dispatches", "−2 serial rounds"), that inventory IS the perf baseline and the substantive review is **claimed vs delivered per verdict id**: does the landed workflow actually remove a *dispatch*, or only narrow a dispatch's payload while keeping the same number of serial steps? Sprint 002's P-8 (impl-test incremental re-entry) is the model case — scope narrowed, zero dispatches removed, so the "−2 to −4 serial dispatches" claim did not land. Also check the reverse direction: return-text-then-orchestrator-writes patterns (audit assembly, reviewer files) buy a serial round but pay the artifact's tokens twice — **except** when the orchestrator had to ingest the full returned text anyway for a gate (reviewer coverage-ledger gate): then persisting a *reduced* form is net-positive and not a finding.

**Diff-scoped fan-out predicates (P-9) — standing answers, do not re-derive.** `asd-phase-impl-review.md` step 5 is the sole SSoT for both predicates.
- The self-hosting UI-surface carve-out (`.asd/templates/*.html` counts as a UI surface when `self_hosting: enabled`) does **not** undermine P-9's savings: it is gated on `self_hosting`, so consumer-mode dispatch frequency is bit-identical to pre-carve-out; the predicate is a strict subset of the pre-P-9 "dispatch UI every iteration" baseline, so dispatch count can never exceed baseline; it re-evaluates per *iteration* from the incremental diff, so html-template edits concentrate in iter 1 and drop out of review-fix iterations; and when it does fire the dispatch is *cheaper* than baseline (reduced rubric — §4 Token comment and §11 Lint exclusions n/a — and 3 fewer input docs, since DESIGN.md/design-system.html/accessibility.html do not exist here). Only 8 files can trigger it (`.asd/templates/*.html`). Worst case: +1 UI dispatch per framework sprint that edits a template. Non-finding.
- Performance-skip predicate is conjunctive (no perf-budgets section AND no executable file in scope); with no budgets in this repo, any `.js` in the diff dispatches me. Expected, not a defect.

**Savings gated behind a new config key never reach existing consumers.** `/asd-update` copies only `release-manifest.json` `managed_paths` (`.asd/rules|templates|agents|skills|workflows|hooks|sync.js`) — `.asd/project/config.yaml` is consumer-owned and never touched, and `t_config.yaml` seeds only *newly initialized* projects. So any new `review.*`/`project.*` flag defaults to whatever the *workflow* does when the field is absent, in every already-installed project including this repo. Check that absent-field handling matches the rule doc's stated default, and that `CHANGELOG.md` tells consumers to add the key. **Confirmed live in sprint 002 `review.scoped_fan_out`**: `t_config.yaml`/`review-policy.md` call `enabled` "the default" while `asd-phase-impl-review.md` step 5 makes an absent field mean *unconditional fan-out* — so P-9's "−6 opus/high dispatches" delivers zero here. Resolution accepted at iter 3: a CHANGELOG "Added" entry now states `absent = disabled` and tells consumers to add `review: { scoped_fan_out: enabled }` by hand; this repo's own `config.yaml` was deliberately left untouched (consumer-owned, out of sprint scope). Do NOT re-raise — the delivery path is documented, and my own dispatch is the expected consequence, not a defect. (Residual wording mismatch at step 5 line 30, which still says "`enabled` (default)" one line after line 29 says absent → skip nothing, is a documentation nit owned by the Documentation reviewer, not me.)

**Skip-gates: check the mechanism matches the justification.** Sprint artifacts (`test-plan.md`, `state.json`, decisions-log, the 7 `reviews/impl/iter-NN/*.md`) are committed between phases, so any gate of the form "recorded sha == `git rev-parse HEAD` → skip" never fires (sprint 002 P-10, pr-phase test/lint skip). **Landed fix, verified correct at iter 3** (`asd-phase-pr.md` step 4 + `sprint-lifecycle.md` "PR phase"): `git diff --quiet <recorded HEAD>...HEAD -- . ':(exclude).asd/sprints/**' ':(exclude).asd/project/**'`, `<recorded HEAD>` = the `HEAD` field in `test-plan.md`'s `Suite run` (written by impl-test step 7, present in `t_test-plan.md`). Re-derivation: recorded HEAD is always an ancestor of HEAD ⇒ `A...HEAD` ≡ `A..HEAD`; every commit in the window lands under `.asd/sprints/**` ⇒ diff empty ⇒ skip fires; a review-fix commit touches real source ⇒ diff non-empty ⇒ suite re-runs. Saving delivers, and it reaches consumers unconditionally (`.asd/workflows` is in `managed_paths`, no config key gates it). Two residual sub-floor hazards worth re-checking if this text is ever edited: `-- .` is CWD-relative (`:/` would be root-anchored), and `':(exclude).asd/project/**'` swallows `commands.yaml` + `stubs.md`, so the prose "no code/test/**stub** change" overstates what the pathspec sees.

**Bounded-growth questions have a standing answer.** `state.json.reviews.impl.iteration_heads` (one `"iter-NN": <sha>` per impl-review iteration, ~55 B) is bounded by `review-policy.md`'s iteration cap of 15 (≈0.9 KB); the user-override path keeps incrementing but grows linearly at 55 B/iteration, and only `iter-(NN-1)` is ever read (direct key lookup, never iterated). Not a concern — confirm in one line, never a finding. Same reasoning applies to any per-iteration map added to `state.json`, and to `verdicts["iter-NN"]` (≤8 keys, see the cost model above).

**Scope reconstruction without a shell:** this agent has no `Bash` tool (tools = Read/Glob/Grep), so a dispatcher instruction like "run this `git diff` yourself" cannot be honored — say so explicitly in the ledger rather than silently trusting the dispatcher's file list, and **count the enumerated list** against the announced total (sprint 002 iter 2 announced 48 and enumerated 51; iter 3's 33, iter 4's 20 and iter 5's 10 matched). Reconstruct changed files from `Glob` results, which are **mtime-ascending (oldest first)** — the iteration's files are the tail. Better still when the sprint has a `plan.md`: its per-task "Affected canonical files" lines give the intended change set per verdict id, which is what the claimed-vs-delivered lens needs anyway.

**Glob truncation trap:** Glob caps output at 100 paths and drops the *overflow* — with mtime-ascending order that silently removes the newest files, i.e. exactly the ones under review. A broad pattern like `.asd/**/*.md` overflows. Narrow until the result count is under 100; a pattern that works repo-wide: `{.asd/rules/*.md,.asd/workflows/*.md,.asd/agents/*.md,.asd/templates/t_*.md,tests/**/*.js,*.md,.asd/*.js,.asd/*.json,.asd/skills/*/SKILL.md}` (~77 hits, excludes `.asd/sprints/**` and `.asd/project/**` which the diff pathspec excludes anyway). Same trap on Grep: a repo-wide `-C` grep for `managed_paths`/pathspecs overflows into a persisted-output file — scope it with `path` to the single file you actually need.

**Note on prior-iteration files:** a repo-wide `Grep` will surface `.asd/sprints/*/reviews/impl/iter-*/` content incidentally. `review-policy.md` forbids *reading* those — scope greps with `path` or a `!sprints/**` glob to avoid it, and disregard any snippet that leaks through. Same applies to Glob: iter-NN review filenames appear in mtime order and are useful as *timeline anchors* (they date each iteration) without opening them.
