In this repo (the ASD framework, `self_hosting: enabled`), `.asd/project/custom-coding-rules.md` has **no perf budgets section** — its three rules are zero-dependency/sync-discipline constraints, not latency/memory/throughput budgets. `custom-common-rules.md` has none either. (Re-verified 2026-09-02, sprint 003 iter 6.) The formal stop condition ("no budgets → APPROVE with note") therefore fires on almost every sprint here.

The only executable surfaces that can carry real perf risk are six files: `.asd/sync.js`, `.asd/skills/asd-update/update.js`, `tests/run.js`, and the three `session-start.js` hooks (two of which are generated).

**Why:** the "product" is agent-runtime instructions, so the closest thing to a perf budget is `AGENTS.md`'s hard rule "Every change must minimize runtime tokens". Treating that as the surrogate budget makes the review substantive instead of a rubber stamp on prose-only sprints.

**How to apply:** when a diff touches none of the six executable files, mark the classic rubric (`anti-patterns`, `algorithmic complexity`, `hot path`) `n/a` with that evidence, but still actively check (a) net prose/token delta against the AGENTS.md rule, and (b) any string that is *executable data* rather than prose — the `':(exclude)…'` git pathspecs in `external-review.md` / `asd-external-review.md` / `t_prompt-external-impl.md` (they size the external-review diff payload; self-hosting row = 5 excludes, `.asd/project`/`.asd/sprints`/`.claude`/`.codex`/`.agents/skills`) and `.asd/release-manifest.json` `managed_paths` cardinality (it sizes what `update.js` parses; `canon_hashes`/`upstream_hashes` churn is value-only and free). Escalate to a real finding only if one of those grows. `managed_paths` is directory-level (7 entries, re-verified sprint 003 iter 6), so file renames *inside* a tracked tree never grow it; manifest top-level shape is 9 keys (`$comment`, `schema_version`, `asd_version`, `repo`, `branch`, `managed_paths`, `model_families`, `canon_hashes`, `upstream_hashes`) — anything else is new and worth a look, but `$comment` is expected, do not flag it. **A fix-round manifest diff that changes only hash *values* for the files edited that round is the expected shape — one line in the ledger, never a finding.** Also cheap and high-value: grep `"model"`/`"effort"` across `.asd/agents/*.md` — a family/effort tier bump is a direct dispatch-cost regression that no other reviewer owns. (Roster re-verified sprint 003 iter 3, 16 agents, tiers unchanged: 7 internal reviewers + BA/architect/UX = opus/high, external = fable/high, PM = opus/medium, both devs + test-engineer = sonnet/medium, `asd-advisor` = fable/medium on Claude but `sol`/medium on Codex. Any deviation is the finding.) When no `.asd/agents/**` file is in the scope list, say so and skip the grep — a tier regression is impossible in that delta.

**Cost model for the two hot-path executables** (established sprint 002 iter 4, the first dispatch here with a real `.js` file in scope):
- `session-start.js` runs once per session and is dominated by Node process startup (~30–50 ms) plus one `readdirSync` of `.asd/sprints/` and one `readFileSync`+`JSON.parse` per sprint dir. Everything downstream of that — `PHASE_CHAIN.indexOf`, `Object.keys(verdicts).sort()`, the verdict scans in `lastReviewVerdict` — operates on collections bounded by *framework structure*, not user input: 11 phases, ≤15 iteration keys (`review-policy.md` cap), and ≤8 verdict entries (7 internal reviewers + external). Three or four sequential short-circuiting `some`/`every` passes over ≤8 strings (iter 5 added a `some(approved)` guard so an all-`skipped:` map reads `mixed`, not `green`), or a regex literal like `/^skipped:/` applied ≤8 times, is unmeasurable against process startup. **Micro-scrutiny of this function is always a non-finding — confirm in one line and move on.** Only a change that adds *filesystem* work per sprint dir, or unbounds one of those collections, is worth a finding.
- `tests/run.js` is ~80+ in-process tests plus a small fixed set of **subprocess spawns** — five, re-verified sprint 003 iter 3: `node .asd/sync.js --check` (section 9), `runHook('claude')`, `runHook('codex')`, and two temp-root `session-start.js` runs. Each spawn costs ~50–150 ms on win32; in-process guards (e.g. the `.asd/templates/*.json` parse guard) are sub-millisecond. **Do not accept "this new test is sub-ms, like the JSON-parse guard" at face value when the test calls `execFileSync`** — it is 2–3 orders of magnitude more, and a dispatcher briefing may assert the wrong premise. It is still not a finding while spawn count grows by a bounded constant. Escalate only if spawns become *per-fixture* (a loop over files each spawning node) — that turns a constant into O(n) on a suite with no parallelism.
- **`tests/run.js` is NOT on any automated hot path — verify before accepting a briefing that says it is.** `commands.yaml` maps `test: node tests/run.js` and `build: node .asd/sync.js --check` as *separate* commands (build does not run the suite), and `.github/workflows/sync-check.yml` runs **only** `node .asd/sync.js --check` on push/PR — it never invokes `tests/run.js`. So the suite runs on deliberate invocation (impl-test, pr-phase re-run) only. Sprint 003 iter 2's dispatcher briefing claimed the suite "runs on every build command invocation"; it does not.
- Directory-driven guards added sprint 003 (sections 9a read-only-agent contract, 9b roster count, 9c `canon_hashes` completeness) are all in-process and correctly shaped: section 9 builds a `Set` of plan targets before its `readdirSync` loop (O(n+m), not O(n·m)), and 9c uses `key in manifest.canon_hashes` (O(1)) rather than an array scan. `readdirSync(.asd/agents)` is now called in 4 separate sections — a *constant* number of readdirs on a 16-entry dir, not per-file work. Non-finding; confirm and move on.

**Claimed-vs-delivered lens (dispatch-cost sprints).** When a sprint's `audit.md` carries a dispatch inventory with per-verdict savings (e.g. sprint 002's `P-N` rows: "−6 opus/high dispatches", "−2 serial rounds"), that inventory IS the perf baseline and the substantive review is **claimed vs delivered per verdict id**: does the landed workflow actually remove a *dispatch*, or only narrow a dispatch's payload while keeping the same number of serial steps? Sprint 002's P-8 (impl-test incremental re-entry) is the model case — scope narrowed, zero dispatches removed, so the "−2 to −4 serial dispatches" claim did not land. Also check the reverse direction: return-text-then-orchestrator-writes patterns (audit assembly, reviewer files) buy a serial round but pay the artifact's tokens twice — **except** when the orchestrator had to ingest the full returned text anyway for a gate (reviewer coverage-ledger gate): then persisting a *reduced* form is net-positive and not a finding.

**`ADVICE_NEEDED` advisor relay (sprint 003) — ALL structural concerns now CLOSED. Do not re-raise any of the three below.** Relay *shape* is the cheapest possible: each of the 10 `asd-phase-*.md` carries exactly ONE line ("On `ADVICE_NEEDED` from any dispatched agent → relay per `sprint-lifecycle.md`'s `ADVICE_NEEDED` protocol; execution resumes, no halt"), one more arm on the pre-existing signal switch — no unconditional dispatch/read/polling, zero marginal cost when it never fires. The 6-step protocol is defined once in `sprint-lifecycle.md` "Signal vocabulary" (not inlined ×10). Unconditional add to the always-loaded corpus ≈ 500 tok/dispatch.
- **Advisor self-recursion: CLOSED (sprint 003 iter 2, re-confirmed iter 3 — not reopened).** Excluded at four levels: `sprint-lifecycle.md` signal entry L209 ("emitter: any dispatched agent other than `asd-advisor`") and protocol step 1 (both operative rule, not comment), `asd-advisor.md` "Signals emitted" lists only `FAILED`, and `core.md` glossary L19 says "never agent-to-agent". Step 4's advisor-`FAILED` path routes to the *user*, not back to the advisor — no loop. The per-workflow relay line's "from any dispatched agent" wording carries no inline exclusion by design; it delegates to protocol step 1, which has it.
- **Cost per consult is DOUBLE a plain dispatch.** Protocol step 3: "Not a same-turn resume (no host tool suspends and resumes a dispatched agent mid-execution — `providers.md` has no such operation); it is a fresh dispatch carrying forward the same task." So one consult = 1 advisor dispatch (fable/medium, cheap) + 1 **full re-dispatch** of the consulting agent, re-paying its whole rules corpus + task context (expensive when that agent is opus/high BA/architect/UX).
- **Consult cap: RESOLVED at sprint 003 iter 3 — the fix is real, not cosmetic.** The iter-2 defect was that the cap's denominator was "per consulting-agent **dispatch**", which step 3 multiplies (each re-dispatch resets it), and that step 6 named *the agent* as enforcer while step 3 injected "no other context" — the enforcing party was the one party that could not know the count. Step 6 now reads: "Capped at 3 consults per consulting-agent **task** — the dispatching phase workflow owns this counter (the consulting agent does not; each re-dispatch in step 3 is a fresh dispatch and would otherwise reset a self-held count), increments it once per completed advisor round-trip, and does not reset it across the task's re-dispatches. At the cap, the workflow stops relaying further `ADVICE_NEEDED` signals for that task". Four independent legs make it enforceable: (1) denominator changed dispatch→task, which is stable across re-dispatches; (2) counter-holder is the workflow, whose execution context is continuous across the dispatches it makes, unlike the agent's; (3) step 3 carves an explicit exception into "no other context injected" for "the running consult count/remaining budget (step 6)", so the count is materialized in the re-dispatch payload; (4) enforcement is workflow-side *refusal to relay*, and the workflow is the sole relay channel (agent-to-agent forbidden), so it needs zero agent cooperation. The counter is workflow-execution-local, not persisted to `state.json` — so a mid-phase crash/resume restarts it at 0, and "task" is looser in design phase (one artifact) than impl (one plan Task). Both are bounded-either-way residuals, sub-high, already considered and dropped; do not raise them as high.
- **The 3 agent files that told their agent "execution resumes in the same turn, no halt" (contradicting step 3's fresh-dispatch semantics): RESOLVED at iter 3 by deletion.** `ADVICE_NEEDED` emission text was removed outright from all four agent files that had it (`asd-pm.md`, `asd-ba.md`, `asd-architect.md`, `asd-ux-designer.md`) rather than corrected in place; `core.md`'s "Autonomy and escalation" rule (L40-45, a Mandatory rule loaded by every agent) is now the sole SSoT for gate-vs-non-gate routing. **Skip-gates: check the mechanism matches the justification.** Sprint artifacts (`test-plan.md`, `state.json`, decisions-log, the 7 `reviews/impl/iter-NN/*.md`) are committed between phases, so any gate of the form "recorded sha == `git rev-parse HEAD` → skip" never fires (sprint 002 P-10, pr-phase test/lint skip). **Landed fix, verified correct at iter 3** (`asd-phase-pr.md` step 4 + `sprint-lifecycle.md` "PR phase"): `git diff --quiet <recorded HEAD>...HEAD -- . ':(exclude).asd/sprints/**' ':(exclude).asd/project/**'`, `<recorded HEAD>` = the `HEAD` field in `test-plan.md`'s `Suite run` (written by impl-test step 7, present in `t_test-plan.md`). Re-derivation: recorded HEAD is always an ancestor of HEAD ⇒ `A...HEAD` ≡ `A..HEAD`; every commit in the window lands under `.asd/sprints/**` ⇒ diff empty ⇒ skip fires; a review-fix commit touches real source ⇒ diff non-empty ⇒ suite re-runs. Saving delivers, and it reaches consumers unconditionally (`.asd/workflows` is in `managed_paths`, no config key gates it). Two residual sub-floor hazards worth re-checking if this text is ever edited: `-- .` is CWD-relative (`:/` would be root-anchored), and `':(exclude).asd/project/**'` swallows `commands.yaml` + `stubs.md`, so the prose "no code/test/**stub** change" overstates what the pathspec sees.

**Bounded-growth questions have a standing answer.** `state.json.reviews.impl.iteration_heads` (one `"iter-NN": <sha>` per impl-review iteration, ~55 B) is bounded by `review-policy.md`'s iteration cap of 15 (≈0.9 KB); the user-override path keeps incrementing but grows linearly at 55 B/iteration, and only `iter-(NN-1)` is ever read (direct key lookup, never iterated). Not a concern — confirm in one line, never a finding. Same reasoning applies to any per-iteration map added to `state.json`, and to `verdicts["iter-NN"]` (≤8 keys, see the cost model above). Likewise `.asd/sync-state.json` (4 fixed entries — only managed-block and json-merge targets, never per-agent) and `release-manifest.json`'s `canon_hashes`/`upstream_hashes` (plain objects keyed by relpath, O(1) lookup; +1 key per new agent at 16 agents) — value-only churn, free.

**Scope reconstruction without a shell:** this agent has no `Bash` tool (tools = Read/Glob/Grep), so a dispatcher instruction like "run this `git diff` yourself" cannot be honored — say so explicitly in the ledger rather than silently trusting the dispatcher's file list, and **count the enumerated list** against the announced total (sprint 002 iter 2 announced 48 and enumerated 51; iter 3's 33, iter 4's 20, iter 5's 10, sprint 003 iter 1's 25, iter 2's 19, iter 3's 13, iter 4's 6, iter 5's 5 and iter 6's 2 matched). Reconstruct changed files from `Glob` results, which are **mtime-ascending (oldest first)** — the iteration's files are the tail. Better still when the sprint has a `plan.md`: its per-task "Affected canonical files" lines give the intended change set per verdict id, which is what the claimed-vs-delivered lens needs anyway. In review-fix iterations the cheapest scope check is `decisions-log.md`'s "impl fix for iter-NN" entry, whose **Affected docs** line should equal the dispatcher's scope list (minus generated views, which the diff pathspec excludes) — plus `.asd/release-manifest.json`, which the post-fix `sync.js --apply` always re-hashes. That entry's **Fixes** line also names each landed change, which is the fastest way to identify *what* to review inside a large file. (Worked exactly this way at sprint 003 iters 5 and 6.)

**Grep gotcha — long lines are silently elided.** `Grep` with `-C`/`-A`/`-B` prints `[Omitted long matching line]` in place of long lines, and both the `ADVICE_NEEDED` protocol's steps and `decisions-log.md`'s **Fixes**/**Decision** lines are exactly that long. A context-grep alone will hide the very sentence under review (this cost a round in sprint 003). When a finding turns on the exact wording of a long line, `Read` the line-number range directly instead of trusting grep context output.

**Glob truncation trap:** Glob caps output at 100 paths and drops the *overflow* — with mtime-ascending order that silently removes the newest files, i.e. exactly the ones under review. A broad pattern like `.asd/**/*.md` overflows. Narrow until the result count is under 100; a pattern that works repo-wide: `{.asd/rules/*.md,.asd/workflows/*.md,.asd/agents/*.md,.asd/templates/t_*.md,tests/**/*.js,*.md,.asd/*.js,.asd/*.json,.asd/skills/*/SKILL.md}` (~77 hits, excludes `.asd/sprints/**` and `.asd/project/**` which the diff pathspec excludes anyway). Same trap on Grep: a repo-wide `-C` grep for `managed_paths`/pathspecs overflows into a persisted-output file — scope it with `path` to the single file you actually need. A `glob:` filter of the form `{a,b}/SKILL.md` silently matches nothing when combined with a `path:` root — pass each file as its own `path:` instead.

**Note on prior-iteration files:** a repo-wide `Grep` will surface `.asd/sprints/*/reviews/impl/iter-*/` content incidentally. `review-policy.md` forbids *reading* those — scope greps with `path` or a `!sprints/**` glob to avoid it, and disregard any snippet that leaks through. Same applies to Glob: iter-NN review filenames appear in mtime order and are useful as *timeline anchors* (they date each iteration) without opening them.
