# Sprint 006-workflow-cost-routing

## Goal
Reduce ASD's model, context, and repeated-work cost while preserving recovery invariants, review obligations, provider restrictions, selected hard human-authority gates, and every machine quality gate. Allow routine user pauses to become adaptive only after this scope is accepted, using recorded authority and objective evidence rather than self-reported confidence. Apply conservative routing: use cheaper execution only for objectively mechanical, narrowly scoped work; keep strong models for risk, ambiguity, expanding scope, and failed checks; and never change the user's selected main model. Keep External Review enabled, make its readiness checks cheap and evidence-based, run wrapper orchestration on `sonnet` or `gpt-5.6-terra` at medium effort, and keep the actual external review on `opus` at high effort or `gpt-5.6-sol` at high effort by default.

Remove the standalone PM delegate unconditionally and transfer its complete orchestration contract to the main phase orchestrator, accepting the loss of PM isolation while preserving state recovery, selected gates, git, archive, release, and ownership controls. The previously requested Batch mechanism remains a separate proposal: assess its feasibility and present it as an explicit user decision before implementation or deferral; neither silently add a generic runner nor silently drop the topic.

## Acceptance
- AC-1: Existing `review.scoped_fan_out` is enabled for this framework and uses complete change-surface evidence to narrow each reviewer to applicable rubric sections without skipping required reviewer agents or weakening review DoD.
- AC-2: Every scoped review emits a compact machine-verifiable coverage ledger whose deterministic validation proves the complete expected file, rule, and section set is represented exactly once as reviewed or `n/a` with a valid predicate; ledger generation is compact in model context as well as on disk, and human-oriented prose is not required.
- AC-3: External Review wrapper orchestration uses `sonnet` at medium effort under Claude Code and `gpt-5.6-terra` at medium effort under Codex. The wrapped actual reviewer explicitly uses Codex CLI with `gpt-5.6-sol` at high effort under Claude Code and Claude CLI with `opus` at high effort under Codex; any per-task downgrade must pass the same objective eligibility rules as other routing, and strong external review is never removed globally. The invocation enforces the wrapped process's actual read-only tool or sandbox boundary, records its resolved model identifier when exposed, and never claims a rolling alias resolved to a dated model without evidence.
- AC-4: External-review preflight runs in the phase orchestrator before wrapper dispatch and diff assembly, using local executable and authentication-status checks that consume no model request. It distinguishes local readiness from proven model access, quota, and reachability: those remain unknown until a bounded actual-model request, preferably the first real review request, supplies evidence.
- AC-5: External-review failures use bounded negative caching with retry-after or expiry and recovery when command, selected model, or authentication state changes. Unknown is never recorded as success; authentication, quota, or reachability failures are not repeatedly retried at model cost; secrets and sensitive command output are never persisted or logged.
- AC-6: The existing transparent availability-skip contract remains intact: each unavailable iteration records a specific `APPROVE (skipped: <reason>)`, the skip satisfies that iteration's DoD, and no availability skip creates a reviewer latch or hides later recovery.
- AC-7: The standalone PM delegate is removed unconditionally. The main phase orchestrator assumes every PM-owned scope, plan, state, approval-gate, manual-step validation, git, PR, archive, and self-hosting release sequence, together with the existing recovery behavior, decision recording, and write allowlists; the accepted loss of PM isolation does not permit any responsibility to disappear.
- AC-8: One live Tester instance is reused within each applicable phase for change analysis, test selection, test authoring or pruning, and test runs, including required approval stops. After session loss or a phase change, work resumes from complete on-disk evidence rather than retained agent context, and reviewer agents are never reused across review dispatches that require fresh context.
- AC-9: Core roles receive only mandatory common rules plus rules and stable reference inputs applicable to their current phase and responsibility. The final routing has no lost invariant, duplicate source of truth, or transcript-only state, and stable inputs are ordered and shaped for provider caching without claiming cache hits or savings that billing evidence does not prove.
- AC-10: Low-cost routing uses commands without a model for deterministic state serialization, file-set enumeration, sync bookkeeping, and other zero-judgment operations; Claude `haiku` with no unsupported effort override and Codex `gpt-5.6-luna` at low effort for objectively mechanical agent work; `sonnet` and `gpt-5.6-terra` at medium effort for normal work; and `opus` and `gpt-5.6-sol` at high effort for risk or ambiguity. Mechanical agent eligibility requires objective inputs and checks, such as an exact repetitive edit with exhaustive match validation or a fixture/test derived from existing behavior with a deterministic check; line count or subjective confidence is never sufficient.
- AC-11: Authentication, security, data migration, public contracts, workflow gates, unfamiliar cross-domain code, ambiguous judgment, and broad repository reasoning start strong. Emerging risk escalates immediately; a newly failed objective check escalates after one bounded correction attempt; infrastructure and authentication failures stay availability handling rather than quality escalation. A cheap creator cannot select a cheap reviewer for its own output: independent review scope and risk determine reviewer eligibility, and a strong reviewer validates experimental cheap-model results. A task never cycles back down, and its tier, reason, selector, and resolved model identifier when available are recorded as resumable evidence.
- AC-12: Routing never changes the user's main model or weakens a role's tools, sandbox, write scope, or instructions. Fixed named generated variants such as `asd-dev-mechanical`, `asd-dev-standard`, and `asd-dev-critical` provide only combinations actually used; they share one canonical role body and permission definition with generated tier metadata rather than hand-maintained copies. Current Codex custom-agent model settings override spawn parameters, so dispatch never mutates a shared generated configuration.
- AC-13: Audit configuration supports `auto`, `always`, and `off` while preserving legacy `enabled` as `always` and `disabled` as `off`. In `auto`, only a known mechanical change with no behavior, contract, migration, or gate impact and a verifiable complete scope may skip audit; unknown or risky scope requires it. The orchestrator shows the reason at the scope gate, freezes the effective boolean in sprint state, and records reevaluation after an accepted scope expansion. This wide self-hosting sprint keeps audit enabled across the entire framework surface.
- AC-14: Canonical `asd-pm` and every generated PM view are removed, with release-manifest, synchronization, orphan cleanup, documentation, and consumer migration behavior updated coherently. All PM responsibilities and phase dispatch sites resolve to the main phase orchestrator after migration, with no compatibility shim that continues to spawn PM.
- AC-15: The existing Architect becomes the default single audit owner for code, documentation, stubs, gaps, and risks. BA joins only when material product or domain ambiguity is evidenced; no new audit agent is added, automatic dual audit fan-out is removed, and the existing `audit.md` artifact, approval gate, and BA/Architect design responsibilities remain available where applicable.
- AC-16: The Batch topic receives a separate feasibility result and explicit user decision before related implementation. The recorded options include implement, defer, and reject with consequences; no generic Batch runner is created merely because it appeared in the earlier bundled proposal.
- AC-17: Canonical rules, agents, workflows, skills, templates, configuration, migrations, model-family mappings, README, and generated Claude/Codex views remain coherent. Applicable parsing, sync, migration, hook, targeted regression, and full repository tests pass with resumable evidence for both providers; capability evidence distinguishes the locally observed Codex CLI 0.150.1 and Claude CLI 2.1.250 behavior from current provider documentation.
- AC-18: One `user_gates` policy supports `adaptive` and `strict`. `strict` restores the previous human pauses, while neither mode removes technical gates. Existing exact user authorization is reused without repeat confirmation; an unreadable or unsupported policy fails closed, and changing modes never classifies a pending hard gate as approved.
- AC-19: In `adaptive`, the orchestrator advances a routine gate only when scope authority and documented constraints cover the choice, effects and affected resources are understood and covered by applicable authority, every applicable check passes, and no unresolved material alternative remains. It records the reason, evidence, artifact revision, and `decision_actor=orchestrator` distinctly from user approval; self-reported confidence is insufficient. Missing facts trigger investigation, while missing preference or authority and unresolved trade-offs go to the user.
- AC-20: Adaptive routine candidates are audit acceptance, plan acceptance, initial impl assessment, green design-review or impl-review handoff, technical ADR choices within an already approved stack and scope, factual tech-reference writes, mechanical documentation or design-system updates, execution of already approved decomposition, and bounded decisions that would otherwise trigger blanket Complication Approval. New expenses, external commitments, sensitive irreversible actions, out-of-scope test deletion, and PR publication are not categorical ASD hard gates; apply the adaptive evidence and authority checks, retaining host permission requirements and test-quality checks. Removing a categorical gate does not itself authorize an unspecified external action or expense. Per-section QODDA microgates use the same eligibility rule rather than a separate pause policy.
- AC-21: Human approval remains hard for new or changed scope, acceptance criteria, user value, or product choices not already explicitly authorized; recording an already fully specified user outcome in `sprint.md` does not create another decision by itself. Approval also remains hard for initial or material UX, brand, accessibility, or stack direction not already authorized; a new subsystem boundary or material architecture, public-contract, or backward-compatibility change; accepting known debt or waiving reviewer findings, coverage, or quality protections; review-iteration-cap override; abort; and sprint closure (finalization and archival). The closure gate is mandatory in both modes: present completion evidence and obtain explicit user approval before finalizing or moving the sprint into the archive; PR publication or a confirmed merge does not substitute for closure approval.
- AC-22: Build, lint, impacted tests, terminal full-suite, coverage-ledger completeness, required reviewer roster and verdicts, and confirmed merge state remain blocking machine checks. The orchestrator never approves or converts a failed or missing technical check into success.
- AC-23: A user or orchestrator approval becomes stale when the governed artifact changes semantically and must be reevaluated under the active policy. The adaptive policy is not used to accept this sprint's current scope or any other pending gate before the policy itself is adopted through the existing scope-acceptance mechanism.

## Out of scope (optional)
- Disabling External Review or treating local CLI/authentication presence as proof of model access, quota, or reachability.
- Globally downgrading agents, changing the user's main model, bypassing selected hard human decisions or machine quality gates, or relaxing reviewer tool and sandbox restrictions.
- Promising savings percentages or cache hits without actual provider billing evidence.
- Implementing or excluding a Batch runner before its explicit feasibility decision.
